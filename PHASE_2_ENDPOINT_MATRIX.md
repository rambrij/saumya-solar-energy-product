# Phase 2 endpoint-by-endpoint security matrix

**Branch:** `audit/phase-2-implementation-gap-analysis`  
**Source:** Spring MVC controller annotations at the current Phase 2 branch HEAD  
**Inventory generated:** 2026-11-10  
**Scope:** Controller method mappings only. Public/authentication endpoints are retained in the inventory and identified by the SecurityConfig allowlist.

## Inventory totals

- 17 controller classes inspected.
- **222 method mapping declarations**.
- 224 expanded route patterns after accounting for multi-path aliases.
- Method distribution: GET 95, POST 93, PUT 4, PATCH 20, DELETE 10.
- `EndpointAuthenticationMatrixTest` discovers Spring's runtime HandlerMethod registry and exercises every non-public mapping without credentials. The expected unauthenticated outcome is HTTP 401 (or 403 where an authorization entry point handles the request); this is only the authentication gate.
- `SecurityConfig` permits only `/api/v1/auth/**`, `/api/v1/public/**`, payment webhook paths, `/uploads/**`, health and API documentation. Every other API mapping requires an authenticated principal.
- After authentication, handlers/services must enforce the applicable account type, role, permission, tenant, customer ownership and (where relevant) branch membership. Missing privilege is expected to return HTTP 403; foreign or non-visible resource identifiers should be consistently hidden with HTTP 404. Public endpoints are exempt only for the specific public operation documented by their handler.
- Each endpoint row below records the common unauthenticated and authenticated-denial contract. The evidence table records which authenticated negative scenarios are actually tested. `PENDING` means no endpoint/resource-specific negative test was found; it must not be interpreted as covered merely because the authentication gate passes.
- CRUD/command coverage remains endpoint-specific; do not infer coverage from the existence of a route, role guard, frontend filter or dynamic authentication test.

## Acceptance rules for closing each row

1. For a read/list route, create same-tenant and foreign-tenant fixtures and prove list exclusion plus guessed-ID 404/403.
2. For create routes, tamper tenant/customer/branch IDs in body, query, headers and accepted JWT claims; verify persisted ownership is derived from the authenticated principal.
3. For update/delete routes, use a real foreign resource ID and assert 404/403 plus unchanged database state.
4. For export/download routes, inspect actual CSV/XLSX/PDF bytes and HTTP download response; verify no foreign record or private storage key leaks.
5. For branch-bearing resources, use two branches in one tenant and one non-admin member assigned to only one branch. Assert assigned-branch rows are visible and other-branch rows are absent.
6. For background jobs, run concurrent workers against MySQL 8.4 and assert state changes and side effects are tenant-scoped and idempotent.

**Current gate:** The dynamic authentication test is broad, but the endpoint-specific CRUD matrix is not yet fully green. The remaining rows must be completed or explicitly deferred with release-owner acceptance before production approval.
